# 问题分级与响应目标

本文是 [SECURITY.md](../SECURITY.md) 响应时效表在 issue 流程中的落地口径：提交 Issue 时按模板选择
severity（阻断 / 严重 / 一般 / 建议），维护者按本表确认分级并执行首次响应与修复目标；安全漏洞
必须走私密通道，**不要**公开披露细节（见 [SECURITY.md · 报告漏洞](../SECURITY.md#报告漏洞)）。

## 维护者与联系方式

- 维护者：UnitSeek 维护团队（仓库与作者信息见 [package.json](../package.json) 的
  `repository` / `author`）；
- 公开问题：GitHub Issues（使用 Bug / 功能模板，按 severity 选择分级）；
- 安全漏洞：GitHub Security Advisories 私密报告（
  [SECURITY.md · 报告漏洞](../SECURITY.md#报告漏洞)），公开 Issue 仅用于非敏感问题。

## 分级与响应目标

| 分级（模板 severity） | 定义与典型场景                                                                                  | 首次响应       | 修复 / 缓解目标                                                          |
| --------------------- | ----------------------------------------------------------------------------------------------- | -------------- | ------------------------------------------------------------------------ |
| `blocker` 阻断        | 数据丢失、静默不更新、无法启动、发布产物缺失等生产不可用或数据正确性问题                        | 1 个工作日     | 优先发布 patch；修复前给出规避说明                                       |
| `critical` 严重       | 核心功能（Store / 集成 / 持久化）不可用且无规避方式，或影响多业务；安全高危按 SECURITY 更严口径 | 2 个工作日     | 10 个工作日内给出修复或缓解方案；安全高危按 72 小时确认 / 7 天修复或缓解 |
| `normal` 一般         | 有明确影响但存在规避方式；文档 / 类型 / 工具链缺陷                                              | 5 个工作日     | 按发布节奏进入下一个 patch / minor，随 CHANGELOG 记录                    |
| `suggestion` 建议     | 改进、体验、文档与新能力想法                                                                    | 5 个工作日确认 | 不承诺修复时间，进入 backlog 由维护者排期（可结合投票）                  |

- **计时口径**：工作日指中国法定工作日（不含周末与法定节假日）；「首次响应」指维护者公开回复并给出
  分级确认或初判；
- 安全漏洞的高危定义、72 小时确认 / 7 天修复或缓解、协调披露，以
  [SECURITY.md · 响应时效](../SECURITY.md#响应时效) 为准，本文不重复覆盖；
- 同一问题可随信息补充升级或降级，调整后按新级别响应（见 [分级调整与标签](#分级调整与标签)）。

## 安全漏洞：私密报告与披露

- **唯一通道**：GitHub Security Advisories 私密报告入口（
  [SECURITY.md · 报告漏洞](../SECURITY.md#报告漏洞)）；不要在公开 Issue、讨论区或 PR 中披露漏洞
  细节、利用方式或受影响用户数据；
- **分级**：安全漏洞由维护者在 Advisory 内按高危 / 一般定级，分别适用 72 小时确认 / 7 天修复或
  缓解、5 个工作日首次响应；
- **协调披露**：修复与披露在 Advisory 内协调；修复发布后按需公开影响面与致谢说明。

## 版本支持窗口与 EOL 公告

- 当前 minor 与上一 minor 获得修复（含安全修复）；更早版本仅处理高危安全漏洞；
- **EOL 提前至少一个 minor 公告**：渠道为 CHANGELOG + Release Notes（见
  [docs/RELEASE.md · 支持窗口](./RELEASE.md#支持窗口) 与
  [Release Notes 模板](./RELEASE-NOTES-TEMPLATE.md#支持窗口)）；
- 每份 Release Notes 的「支持窗口」段为**必填**：写明适用版本范围、EOL 计划与下一版本计划；
  首次发布同样按模板声明，不适用时显式写「不适用」。

## 复盘要求

- **触发条件**：数据丢失 / 静默不更新 / 发布事故 / 高危安全漏洞等重大故障；
- **时限与产出**：修复发布后 5 个工作日内完成复盘，记录时间线、根因、影响面、改进项与 owner；
- **归档与跟踪**：复盘结论进入 CHANGELOG / Release Notes（或维护者文档），改进项建 Issue 跟踪
  并标注对应分级，直至闭环。

## 分级调整与标签

- 维护者可在 Issue 上调整 severity 并说明理由（评论 + 标签），调整后按新级别响应；
- 标签约定：`blocker` / `critical` / `normal` / `suggestion` 与分级一一对应；安全相关公开
  Issue 加 `security` 标签（已披露或非敏感），未披露漏洞一律走私密 Advisory；
- 模板默认标签：Bug 模板 `bug`，功能模板 `enhancement`；severity 由提交者选择、维护者确认。
